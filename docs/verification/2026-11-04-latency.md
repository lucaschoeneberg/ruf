# Latency investigation and bounded audio profile change

## Findings

The pinned baresip configuration default is a fixed audio jitter buffer with
100 ms minimum, 200 ms maximum and 50 packet slots. Our bridge previously
inherited those values. The native implementation clamps playout time to the
minimum; fixed mode does not adapt its offset to measured jitter.

The bridge now explicitly selects the existing adaptive implementation with a
40–200 ms delay range. No dependency, frontend command, DTO, codec, packetization,
hardware driver, NAT logic or network setting changed. Reuse of the existing
configuration parser keeps the patch to the bridge's startup configuration.
The native profile applies when starting a new engine; a running app retains its
previous profile until restarted.

## Native component measurement

`crates/baresip-adapter/native/latency_probe.c` links to the actual staged
baresip/re static libraries. It uses a virtual RTP clock, 8 kHz timestamps and
100 synthetic packets at 20 ms spacing. It does not place calls or access audio
hardware. The reference and proposed profiles are explicit inputs to this
comparison, not an end-to-end measurement of the app's configuration.

| Scenario                                          | First playout | Packets played | Insertion errors |
| ------------------------------------------------- | ------------: | -------------: | ---------------: |
| Fixed minimum 100 ms, no jitter                   |        100 ms |      100 / 100 |                0 |
| Adaptive minimum 40 ms, no jitter                 |         40 ms |      100 / 100 |                0 |
| Fixed minimum 100 ms, 0–12 ms arrival variation   |        100 ms |      100 / 100 |                0 |
| Adaptive minimum 40 ms, 0–12 ms arrival variation |         40 ms |      100 / 100 |                0 |

This demonstrates 60 ms less initial playout delay **in this component** under
these conditions. It is not a measured 60 ms reduction in full call latency.
The adaptive buffer may increase delay under jitter. Larger spikes, loss,
reordering, hardware underruns and remote PBX buffering require separate tests.

## Other latency contributors

- CoreAudio's output module prequeues six buffers. At the default 20 ms packet
  time these have 120 ms nominal total capacity. Capacity is not a standalone
  microphone-to-speaker measurement. Reducing this queue requires real-device
  loopback and underrun tests; its count was left unchanged. The three capture
  buffers are reusable buffers, not evidence of three packets of capture delay.
- Audio playback buffering defaults to 20–160 ms. The upper bound is a capacity
  limit, not an unconditional 160 ms delay. It was left unchanged.
- Account packetization defaults to 20 ms. Reducing it increases packet rate and
  was not needed for this bounded change.
- The main UI polls every 500 ms. That can delay status display independently of
  native SIP processing/audio. No UI polling or event-delivery changes were made.
- A filtered read-only Tailscale status check reported a direct subnet-router
  connection. Five Tailscale disco pings returned direct responses: minimum
  15 ms, median 22 ms, maximum 100 ms, no DERP replies. This is a small control
  sample of router round-trip timing, not one-way RTP jitter or audio latency.
  No peer names/addresses were recorded and no VPN settings changed.

## Validation

- Native component comparison passed all four scenarios above.
- `bun run test:asterisk`: all four native interop tests passed, including NAT
  remote termination and call-slot reuse. RTP echo remains valid.
- `bun run test:sip-diagnostics`: passed, including remote BYE's 200 response and
  restricted/default-off diagnostic behavior.
- Native workspace Clippy with warnings denied and Cargo tests passed.
- Native macOS bundle and final formatting checks recorded below after completion.

Real microphone-to-speaker latency on the user's UniFi Talk/Tailscale setup,
CoreAudio device latency and Windows runtime were not measured. Network
configuration remained unchanged. Native APIs/DTOs were reused; the internal
profile behavior is documented in `docs/api/README.md` and `native/README.md`.

Final checks passed: native desktop `.app` build, signed microphone entitlement
check, workspace formatting and `git diff --check`. The rebuilt artifact is in
ignored `native/build/low-latency/SIP.app`. The currently running NAT-fix app was
not restarted as part of this latency change; the new profile applies when the
rebuilt app starts. No frontend/API contract changed. Native smoke retained
mono 8 kHz G.711 echo; this is media integrity evidence, not hardware latency.

## User-operated deployment check

The low-latency native bundle was subsequently started with diagnostics. Its
binary contains the adaptive 40–200 ms startup profile. The user's real
UniFi Talk/Tailscale test produced two clean remote-termination sequences:
received BYE, transmitted 200 OK, native closed, with no local BYE.

This session trace carries no RTP timing, current adaptive-buffer delay or
microphone-to-speaker timing measurement. It confirms signaling behavior and
the selected build/profile, but cannot confirm a 60 ms improvement in complete
call latency. The 60 ms result remains the isolated native virtual-clock
comparison above. No additional test call or network changes were needed for
this analysis.
